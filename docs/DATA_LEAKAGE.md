# Data Leakage Review

Scope: both marketing datasets (bank-full.csv, bank-additional-full.csv). No leakage-relevant variables were found in churn_prediction.csv beyond the target itself; that is noted at the end of this document.

| Variable | Dataset | Why it causes leakage | Prediction scenario affected | Excluded | Justification |
|---|---|---|---|---|---|
| duration | bank-full.csv, bank-additional-full.csv | Call length is only known once the call has happened and ended. A call that ends in 0 seconds essentially guarantees no subscription, and a long call is strongly associated with a completed, engaged conversation. The source documentation for bank-additional-full.csv states this directly: the variable "highly affects the output target" and "is not known before a call is performed," and should only be used for benchmark comparisons, not a realistic model. | Predicting whether a customer will subscribe before or during a campaign contact | Yes, for any model meant to guide who to call. Retained only in a benchmark comparison, clearly labeled as unrealistic, if Agent 2 wants to show the effect of including it. | Using duration to predict subscription answers "did this call go well," not "should we call this customer." Confirmed by the dataset's own documentation, not just by inspection. |
| pdays (raw sentinel form) | bank-full.csv, bank-additional-full.csv | Not a leakage variable in the causal sense, but the -1 / 999 "never contacted" sentinel value sits inside a numeric column and will distort any model or statistic that treats it as an ordinary day count. Flagged here because it is a data integrity issue with the same downstream effect as leakage: a model can appear to "learn" a spurious relationship from the sentinel rather than from any real signal. | Any model using pdays as a raw numeric feature | Not excluded, but must be split into a binary "previously contacted" flag and a numeric day count for the contacted subset before modeling | The information itself is legitimate and available before the call; it just needs correct encoding, not removal. |
| poutcome = unknown / default = unknown | bank-full.csv, bank-additional-full.csv | Not leakage. Included here to flag that "unknown" functions as a missing-value marker, not a real category with predictive meaning. In bank-full.csv, poutcome is unknown for 81.75% of rows, which limits how much signal that column can realistically provide regardless of encoding. | Any model using poutcome or default as encoded categorical features | Not excluded, but must be treated explicitly as its own category or imputed with a documented method, not silently one-hot encoded as if it were an ordinary label | Same reasoning as pdays: an encoding issue, not a temporal leakage issue, but it affects the same downstream models. |

## churn_prediction.csv

No variable in this file records information that occurs strictly after the churn outcome in a way that would leak the target. The balance and transaction columns (current_balance, current_month_credit, etc.) are described as current-period figures, and churn is a status at the same point in time, not a future event relative to these columns based on the data as supplied. This should be revisited once cleaning is underway in case any column turns out, on closer inspection, to be computed using post-churn data (for example, a "current" balance that is actually captured after an account was already closed). No such case was found during this audit.

## Basis for this review

Findings for `duration` are supported directly by the dataset's own documentation (bank-additional-names.txt), not by inference alone. All other entries are based on inspection of the actual column values described in DATA_AUDIT.md.
